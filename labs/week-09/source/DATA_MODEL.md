## 1. ภาพรวม

```
+-------------------+       1:N        +------------------------+
|       users       | <-------------- |        requests        |
+-------------------+                 +------------------------+
| id (PK)           |                 | id (PK)                |
| name              |                 | requester_id (FK)      |
| department        |                 | request_type           |
| email (UNIQUE)    |                 | location               |
+-------------------+                 | details                |
                                       | priority               |
                                       | status                 |
                                       | created_at             |
                                       +------------------------+
```

**One-to-One (1:1):** ฝั่งละ 1 ตัวเลือก เช่น คน 1 คน มีบัตรประชาชน 1 ใบ

**One-to-Many (1:N):** ฝั่งหนึ่งมีได้หลายตัวเลือก (ใช้ในโปรเจกต์เรา) เช่น ผู้ใช้ 1 คน ส่งคำร้องได้หลายใบ

**Many-to-Many (M:N):** จับคู่ไขว้กันได้หลายตัวทั้งสองฝั่ง เช่น นักศึกษาหลายคน เรียนหลายวิชา (ต้องมีตารางกลางช่วยเชื่อม)

## 2. ทำไมต้องแยกเป็น 2 ตาราง

การที่เราเปลี่ยนมาแยกตารางแทนการเก็บชื่อตรงๆ แบบตอน Week 06–07 ช่วยแก้ปัญหาหลักๆ ได้คือ

**ปัญหาข้อมูลซ้ำซ้อน (Data Redundancy):**
หากใช้วิธีเดิมที่เอาชื่อ แผนก หรืออีเมลของผู้แจ้งไปพิมพ์เก็บเป็นข้อความตรงๆ ในตารางคำร้องทุกใบ เมื่อผู้ใช้งาน 1 คน ส่งคำร้องเข้ามาหลายๆ ครั้ง ข้อมูลส่วนตัวเดิมๆ ก็จะต้องถูกบันทึกซ้ำซ้อนกันวนไปทุกแถวโดยไม่จำเป็น ทำให้เปลืองพื้นที่จัดเก็บฐานข้อมูลโดยใช่เหตุ

**ปัญหาความไม่สอดคล้องของข้อมูล (Data Anomaly) และความยุ่งยากในการแก้ไข:**
ลองนึกภาพตามคำถามนี้ดูครับ: "ถ้าสมชายเปลี่ยนชื่อ ต้องแก้กี่ที่?" หากเก็บเป็นข้อความธรรมดาและสมชายเคยส่งคำร้องมาแล้ว 10 ใบ เราจะต้องตามไปไล่แก้ข้อมูลให้ครบทั้ง 10 แถว ซึ่งเสี่ยงต่อการหลงลืม ตกหล่น และอาจทำให้ข้อมูลในระบบเกิดความขัดแย้งผิดเพี้ยนได้ง่าย

**ปัญหาความเสี่ยงด้านความถูกต้องของข้อมูล (Data Integrity):**
เมื่อไม่มีการควบคุมข้อมูลผู้ใช้ด้วยตารางหลัก (Master Table) มีโอกาสสูงที่ผู้ใช้งานคนเดิมจะพิมพ์ชื่อสะกดผิด หรือใช้อีเมลต่างกันในแต่ละครั้งที่ส่งคำร้อง ทำให้ระบบมองว่าเป็นคนละคนกันและไม่สามารถตรวจสอบสถิติที่แท้จริงได้

## 3. รายละเอียดตาราง

### ตาราง `users`

เก็บข้อมูลผู้ใช้งานในระบบ

| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด | คำอธิบาย |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY, AUTOINCREMENT | รหัสประจำตัวผู้ใช้ มีการ create เลขอัตโนมัติ |
| `name` | TEXT | NOT NULL | ชื่อ-นามสกุลของผู้ใช้งาน ต้องบังคับใส่เพื่อระบุเจ้าของบัญชี |
| `department` | TEXT | NOT NULL | คณะแผนก ใช้คัดแยกนักศึกษาว่าอยู่ คณะไหน |
| `email` | TEXT | NOT NULL, UNIQUE | อีเมลติดต่อ ห้ามว่างและห้ามซ้ำ ใช้เป็นข้อมูลระบุตัวตนที่ไม่ซ้ำกัน |

### ตาราง `requests`

เก็บข้อมูลคำร้องขอรับบริการที่ผู้ใช้แจ้งเข้ามา

| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด | คำอธิบาย |
|---|---|---|---|
| `id` | TEXT | PRIMARY KEY | รหัสคำร้องแบบกำหนดรูปแบบเอง (เช่น `REQ-001`) เพื่อระบุลำดับคำร้องขอ |
| `requester_id` | INTEGER | NOT NULL, FOREIGN KEY → `users(id)` | เชื่อมความสัมพันธ์กับตาราง `users` เพื่อบังคับว่าทุกคำร้องต้องมีผู้แจ้งอยู่ในระบบจริง |
| `request_type` | TEXT | NOT NULL, CHECK | ประเภทของคำร้อง จำกัดให้เลือกเฉพาะค่าที่กำหนดไว้ ป้องกันข้อมูลผิดพลาด |
| `location` | TEXT | NOT NULL | สถานที่เกิดเหตุ/รับบริการ ห้ามเว้นว่าง เพื่อให้ทีมงานทราบจุดที่ต้องเข้าไปปฏิบัติงาน |
| `details` | TEXT | NOT NULL | รายละเอียดอธิบายปัญหา บังคับระบุเพื่อให้เข้าใจความต้องการและสาเหตุ |
| `priority` | TEXT | NOT NULL, DEFAULT | ระดับความเร่งด่วน ค่าเริ่มต้นคือ `normal` และ เรงด่วนคือ `urgent` |
| `status` | TEXT | NOT NULL, DEFAULT | สถานะของคำร้อง เช่น `pending`, `in-progress`, `completed` ควบคุมด้วย CHECK ให้เป็นไปตามขั้นตอนการทำงานจริง |
| `created_at` | TEXT | NOT NULL, DEFAULT | เวลาที่สร้างคำร้อง บันทึกอัตโนมัติด้วยฟังก์ชันเวลาปัจจุบัน เพื่อให้ตรวจสอบลำดับก่อน-หลังได้ |

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

**ทำไม `users.id` กับ `requests.id` ถึงใช้ชนิดข้อมูลต่างกัน?**

`users.id` เลือกใช้ชนิด INTEGER แบบ AUTOINCREMENT เพราะเป็นตารางข้อมูลผู้ใช้งานหลักที่จำนวนแถวจะเพิ่มขึ้นเรื่อยๆ การใช้ตัวเลขรันอัตโนมัติช่วยให้ระบบจัดการ ค้นหา และทำดัชนี (Indexing) ได้อย่างรวดเร็วและมีประสิทธิภาพสูงสุด

`requests.id` เลือกใช้ชนิด TEXT (เช่น รูปแบบรหัส REQ-001) เพราะต้องการให้รหัสคำร้องมีความหมาย อ่านปุ๊บแล้วเข้าใจทันทีว่าเป็นรหัส Request อีกทั้งยังช่วยให้การแสดงผลบนหน้าเว็บไซต์หรือระบบแจ้งเตือนมีความเป็นระเบียบและสื่อสารกับผู้ใช้ได้ง่ายกว่าการใช้ตัวเลขเพียวๆ

**ทำไมต้องมี CHECK constraint ทั้งที่ API ก็ตรวจข้อมูลอยู่แล้ว?**

เพราะฐานข้อมูลคือด่านสุดท้ายที่ต้องปลอดภัยที่สุด (Last Line of Defense) แม้ว่าฝั่ง API หรือหน้าบ้าน (Frontend) จะมีการตรวจสอบความถูกต้องของข้อมูล (Validation) มาก่อนแล้ว แต่ถ้าวันหนึ่งมีการเพิ่มข้อมูลผ่านช่องทางอื่น เช่น รันสคริปต์ตรงผ่าน CLI หรือเกิดข้อผิดพลาดทำให้ระบบ API ถูกข้าม (Bypass) ไป ตัว CHECK constraint ในฐานข้อมูลจะเป็นเกราะป้องกันตัวสุดท้ายที่ช่วยการันตีความถูกต้องและสมบูรณ์ของข้อมูล (Data Integrity) ไม่ให้ข้อมูลที่ผิดกฎหลุดรอดเข้ามาบันทึกในระบบได้เด็ดขาด

## 5. ตัวอย่างการใช้ JOIN

ตัวอย่าง Code JOIN + WHERE เพื่อกรองหาคำว่าไฟฟ้า

```sql
SELECT u.name, u.department, r.request_type, r.location, r.details
FROM requests r
JOIN users u ON u.id = r.requester_id
WHERE u.department LIKE '%ไฟฟ้า%'
ORDER BY u.id;
```

**ผลลัพธ์**

| name | department | request_type | location | details |
|---|---|---|---|---|
| ปริวัตต์ เทพอินทร์ | วิศวกรรมไฟฟ้า | ขอใช้อุปกรณ์ | ห้องประชุม 2 | ขอยืมโปรเจกเตอร์สำหรับนำเสนอโครงงาน |

## 6. ข้อสังเกตสำหรับสัปดาห์ที่ 10

**โครงสร้างและการจัดเก็บข้อมูล:** ผลลัพธ์จากการทำ JOIN ในฐานข้อมูลแสดงให้เห็นว่าข้อมูลถูกดึงมาจากตารางที่แยกอิสระจากกัน (ตาราง users และ requests) แล้วนำมาเชื่อมโยงกันผ่านความสัมพันธ์ ทำให้ข้อมูลมีความถูกต้องตามหลักฐานข้อมูลเชิงสัมพันธ์และไม่เกิดความซ้ำซ้อน ในขณะที่ข้อมูล JSON ของ Week 07 อยู่ในรูปของ Object เดี่ยวที่มีการฝังชื่อผู้แจ้ง (requesterName) รวมเป็นข้อความเดียวกันกับคำร้องโดยตรง

**การจัดการเมื่อมีการเปลี่ยนแปลงข้อมูล:** หากข้อมูลของตัวผู้ใช้งานมีการเปลี่ยนแปลง (เช่น เปลี่ยนชื่อหรืออีเมล) ฝั่งฐานข้อมูลที่มีการแยกตารางและใช้ JOIN จะรองรับการอัปเดตที่จุดเดียวในตาราง users โดยที่ข้อมูลทุกรายการจะสะท้อนค่าปัจจุบันทันที ต่างจากโครงสร้าง JSON แบบเดิมใน Week 07 ที่หากชื่อผู้แจ้งเปลี่ยนไป ข้อมูลในตารางคำร้องทุกแถวที่มีชื่อนั้นจะต้องถูกตามไปแก้ไขทีละรายการ ซึ่งเสี่ยงต่อความไม่สอดคล้องของข้อมูลในระบบ

## 7. CP25 · ทดสอบ constraint

| # | ลองทำ | ต้องได้ error |
|---|---|---|
| ① | ใส่คำร้องที่ `requester_id = 99999` | FOREIGN KEY constraint failed |
| ② | ใส่ `status = 'ยกเลิก'` | CHECK constraint failed |
| ③ | ใส่อีเมลซ้ำกับคนที่มีอยู่ | UNIQUE constraint failed |
| ④ | ใส่คำร้องที่ `id` ซ้ำ | UNIQUE constraint failed |
| ⑤ | ใส่คำร้องโดยไม่ระบุ `location` | NOT NULL constraint failed |

### ผลการทดสอบ Constraint

**1. ใส่คำร้องที่ requester_id = 99999**

คำสั่งที่ลอง

```sql
INSERT INTO requests (id, requester_id, request_type, location, details)
VALUES ('REQ-TEST', 99999, 'แจ้งซ่อม', 'ห้องทดสอบ', 'ทดสอบระบบ');
```

ผลลัพธ์

```
FOREIGN KEY constraint failed
```

**2. ใส่ status = 'ยกเลิก'**

คำสั่งที่ลอง

```sql
INSERT INTO requests (id, requester_id, request_type, location, details, status)
VALUES ('REQ-TEST2', 1, 'แจ้งซ่อม', 'ห้องทดสอบ', 'ทดสอบระบบ', 'ยกเลิก');
```

ผลลัพธ์

```
CHECK constraint failed: status IN ('pending' , 'in-progress' , 'completed') (19)
```

**3. ใส่อีเมลซ้ำกับคนที่มีอยู่**

คำสั่งที่ลอง

```sql
INSERT INTO users (name, department, email)
VALUES ('ทดสอบ ชื่อ', 'วิศวกรรม', 'aungkanr@rmutl.ac.th');
```

ผลลัพธ์

```
UNIQUE constraint failed: user.email (19)
```

**4. ใส่คำร้องที่ id ซ้ำ**

คำสั่งที่ลอง

```sql
INSERT INTO requests (id, requester_id, request_type, location, details)
VALUES ('REQ-001', 1, 'แจ้งซ่อม', 'ห้องทดสอบ', 'ทดสอบระบบ');
```

ผลลัพธ์

```
UNIQUE constraint failed: requests.id (19)
```

**5. ใส่คำร้องโดยไม่ระบุ location**

คำสั่งที่ลอง

```sql
INSERT INTO requests (id, requester_id, request_type, details)
VALUES ('REQ-TEST5', 1, 'ทดสอบระบบ');
```

ผลลัพธ์

```
Parse error: 3 values for 4 columns
```
