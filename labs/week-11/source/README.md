# Campus Service Request System

ระบบรับแจ้งคำร้องและติดตามสถานะบริการภายในมหาวิทยาลัยสำหรับนักศึกษาและบุคลากร

---

## ภาพรวม

ระบบ Campus Service Request พัฒนาขึ้นเพื่อให้ผู้ใช้งานสามารถสร้างคำร้อง แจ้งซ่อม หรือขอใช้บริการสถานที่และอุปกรณ์ต่างๆ พร้อมติดตามสถานะแบบเรียลไทม์

### เทคโนโลยีที่ใช้

| ส่วนงาน | เทคโนโลยี |
|---|---|
| Frontend | React, React Router DOM, Vite |
| Backend (API) | Node.js, Express.js |
| Database | SQLite (`node:sqlite`) |

> หมายเหตุ: โมดูล `node:sqlite` ต้องใช้ Node.js เวอร์ชันใหม่ (แนะนำ v22.13 ขึ้นไป)

---

## สถาปัตยกรรม 3 ชั้น

ระบบนี้แบ่งการทำงานเป็น 3 ชั้น โดยแต่ละชั้นมีหน้าที่ของตัวเองและคุยกับชั้นที่อยู่ติดกันเท่านั้น เปรียบเทียบง่ายๆ เหมือนร้านอาหาร

- **Frontend** เหมือนพนักงานหน้าร้าน คอยรับออเดอร์จากลูกค้าและนำอาหารไปเสิร์ฟ
- **API** เหมือนครัว ตรวจว่าออเดอร์ถูกต้องไหม แล้วจัดการทำตามขั้นตอน
- **Database** เหมือนสมุดบัญชีและห้องเก็บของ จดและเก็บทุกอย่างไว้ไม่ให้หาย

```text
[React] ──HTTP/JSON──> [Express] ──SQL rows──> [SQLite]
```

### หน้าที่ของแต่ละชั้น

| ชั้น | หน้าที่ | โฟลเดอร์ |
|---|---|---|
| Frontend | หน้าจอผู้ใช้ แสดงผล UI และรับการกด/กรอกข้อมูล | `frontend/` |
| API | จัดการ route · controller · service และตรวจสอบข้อมูล | `api/src/` |
| Database | จัดเก็บข้อมูลผู้ใช้งานและคำร้องอย่างคงทน | `api/data/` |

**Frontend (React)**
คือทุกอย่างที่ผู้ใช้มองเห็นและกดได้ เช่น ฟอร์มสร้างคำร้อง รายการคำร้อง และหน้าดูสถานะ ชั้นนี้ไม่เก็บข้อมูลถาวรและไม่ตัดสินใจเรื่องกฎของระบบ มีหน้าที่แค่รับสิ่งที่ผู้ใช้กรอก ส่งไปถาม API แล้วนำคำตอบมาแสดงผล

**API (Express)**
คือสมองของระบบ รับคำขอจาก Frontend ตรวจสอบว่าข้อมูลถูกต้อง ทำตามกฎของระบบ แล้วค่อยไปอ่านหรือเขียนฐานข้อมูล ภายในชั้นนี้แบ่งย่อยออกเป็นอีก 3 ส่วน

| ส่วนย่อย | ทำหน้าที่อะไร |
|---|---|
| Route | เหมือนป้ายบอกทาง ดูว่าคำขอที่เข้ามาคือเรื่องอะไร (เช่น สร้างคำร้อง หรือดูสถานะ) แล้วส่งต่อให้ถูกคน |
| Controller | เหมือนผู้ประสานงาน รับคำขอ เรียก service ให้ทำงาน แล้วจัดคำตอบส่งกลับไปให้ Frontend |
| Service | เหมือนคนทำงานจริง เก็บกฎและขั้นตอนของระบบ (Business Logic) และเป็นส่วนเดียวที่คุยกับฐานข้อมูล |

นอกจากนี้ยังมีการตรวจสอบข้อมูล (Validation) เพื่อกันข้อมูลที่ไม่ครบหรือผิดรูปแบบไม่ให้เข้าไปถึงฐานข้อมูล

**Database (SQLite)**
คือที่เก็บข้อมูลผู้ใช้งานและคำร้องทั้งหมดไว้ในไฟล์ `campus.db` ข้อมูลจะยังอยู่ครบแม้ปิดเซิร์ฟเวอร์แล้วเปิดใหม่ และมีเพียง API เท่านั้นที่เข้าถึงได้ Frontend ไม่เคยต่อกับฐานข้อมูลโดยตรง

### Flow การทำงาน

เมื่อผู้ใช้ทำอะไรสักอย่างบนหน้าเว็บ คำขอจะเดินทางลงไปทีละชั้น แล้วคำตอบจะเดินทางย้อนกลับขึ้นมาตามเส้นทางเดิม

```text
  ผู้ใช้
    │  1. กรอกฟอร์มแล้วกดส่ง
    ▼
┌────────────────────────┐
│ Frontend (React)       │
└───────────┬────────────┘
            │  2. ส่งคำขอ HTTP พร้อมข้อมูลแบบ JSON
            ▼
┌────────────────────────┐
│ API (Express)          │
│  Route                 │  3. ดูว่าคำขอเรื่องอะไร ส่งให้ถูกที่
│   └─ Validation        │  4. ตรวจว่าข้อมูลครบและถูกต้อง
│       └─ Controller    │  5. รับเรื่องและเรียก Service
│           └─ Service   │  6. ทำตามกฎของระบบ
└───────────┬────────────┘
            │  7. สั่งอ่านหรือเขียนข้อมูลด้วย SQL
            ▼
┌────────────────────────┐
│ Database (SQLite)      │  8. บันทึก/ดึงข้อมูล แล้วส่งผลลัพธ์กลับ
└───────────┬────────────┘
            │  9. ผลลัพธ์ย้อนกลับขึ้นไปตามเส้นทางเดิม
            ▼
   API สรุปผลเป็น JSON ส่งกลับ  ──>  Frontend อัปเดตหน้าจอ  ──>  ผู้ใช้เห็นผล
```

### ตัวอย่าง: นักศึกษาแจ้งซ่อมแอร์ในห้องเรียน

1. นักศึกษากรอกรายละเอียดในฟอร์มแล้วกดส่ง
2. Frontend ส่งข้อมูลไปให้ API
3. API ตรวจว่ากรอกครบหรือไม่ ถ้าไม่ครบจะตอบกลับทันทีว่าขาดอะไร โดยไม่แตะฐานข้อมูล
4. ถ้าครบ Service จะบันทึกคำร้องลงฐานข้อมูล พร้อมสถานะเริ่มต้น
5. API ส่งผลกลับไปว่าบันทึกสำเร็จ
6. Frontend แสดงคำร้องใหม่ให้นักศึกษาเห็นและติดตามสถานะต่อได้

## วิธีรันระบบ

### 1. การเตรียมระบบครั้งแรก (First-time Setup)

ก่อนเริ่มรัน ให้เตรียมไฟล์คอนฟิกและฐานข้อมูล SQLite ดังนี้

```bash
# 1. เข้าโฟลเดอร์ api เพื่อติดตั้ง dependencies และสร้างฐานข้อมูล
cd api
npm install
cp .env.example .env
npm run db:setup      # สร้าง campus.db จาก schema.sql

# 2. เข้าโฟลเดอร์ frontend เพื่อติดตั้ง dependencies
cd ../frontend
npm install
```

### 2. วิธีรันในโหมดพัฒนา (Development Mode)

ในโหมดพัฒนา จะเปิดทำงานแยกกัน 2 Processes (2 Terminal) เพื่อให้ Vite ทำงานแบบ Hot Reload ได้

**Terminal 1: Backend API Server**

```bash
cd api
npm run dev
```

API จะทำงานที่ http://localhost:3001

**Terminal 2: Frontend React Dev Server**

```bash
cd frontend
npm run dev
```

หน้าเว็บจะทำงานที่ http://localhost:5173

### 3. วิธีรันในโหมดใช้งานจริง (Production Mode)

ในโหมด Production จะ Build ไฟล์ Frontend เป็น Static ทั้งหมด แล้วให้ Express API เป็นผู้เสิร์ฟทั้งเว็บและ API บนพอร์ตเดียว (`3001`)

**ขั้นที่ 1: Build ไฟล์ Frontend**

```bash
cd frontend
npm run build
```

**ขั้นที่ 2: สั่งรัน API ในโหมด Production**

Linux / macOS

```bash
cd ../api
NODE_ENV=production npm start
```

Windows (PowerShell)

```powershell
cd ..\api
$env:NODE_ENV="production"; npm start
```

## Environment Variables

รายการตัวแปรสภาพแวดล้อมที่รองรับในระบบ

| ตัวแปร | ความหมาย / หน้าที่ | ค่าเริ่มต้น (Default) |
|---|---|---|
| `NODE_ENV` | โหมดการทำงานของระบบ (development / production) | `development` |
| `PORT` | หมายเลขพอร์ตสำหรับ API Server | `3001` |
| `CORS_ORIGIN` | URL ฝั่ง Frontend ที่อนุญาตให้เรียกใช้งาน API | `http://localhost:5173` |
| `DB_FILE` | พาธสำหรับจัดเก็บไฟล์ฐานข้อมูล SQLite | `./data/campus.db` |
| `STATIC_DIR` | พาธจัดเก็บไฟล์ Frontend Build ในโหมด Production | `../frontend/dist` |

## การตัดสินใจออกแบบ

หัวข้อนี้อธิบายว่าทำไมระบบถึงออกแบบมาแบบนี้ เพื่อให้คนที่มาพัฒนาต่อเข้าใจเหตุผล ไม่ใช่แค่เห็นว่าโค้ดเป็นอย่างไร

### ทำไมแยกเป็น 3 ชั้น

ถ้าเอาทุกอย่างมารวมไว้ที่เดียว พอจะแก้อะไรสักจุดก็มักไปกระทบจุดอื่นโดยไม่ตั้งใจ การแยกหน้าที่กันอย่างชัดเจน (Separation of Concerns) จึงช่วยได้หลายอย่าง

- **ทดสอบง่าย** ตรวจเฉพาะส่วนที่สงสัยได้ โดยไม่ต้องเปิดทั้งระบบ
- **แก้หน้าตาได้อิสระ** จะปรับดีไซน์หรือเปลี่ยนหน้าจอเมื่อไรก็ได้ โดยไม่กระทบกฎของระบบใน API
- **ขยายระบบได้ในอนาคต** ถ้าผู้ใช้เยอะขึ้น สามารถแยกแต่ละชั้นไปรันคนละเซิร์ฟเวอร์ได้ทันที

### ทำไมแยกโค้ดใน API เป็น Route, Controller, Service

เป้าหมายคือให้โค้ดแต่ละไฟล์ทำหน้าที่เดียว เวลาเกิดปัญหาจะรู้ทันทีว่าต้องไปดูตรงไหน

- ปัญหาเรื่องเส้นทางหรือ URL ให้ดูที่ Route
- ปัญหาเรื่องการรับ-ส่งข้อมูลให้ดูที่ Controller
- ปัญหาเรื่องกฎหรือขั้นตอนของระบบให้ดูที่ Service

นอกจากนี้ถ้าวันหนึ่งต้องเพิ่มช่องทางใหม่ เช่น แอปมือถือ ก็นำ Service ชุดเดิมกลับมาใช้ได้เลย ไม่ต้องเขียนกฎซ้ำ

### ทำไมต้องตรวจสอบข้อมูลที่ฝั่ง API

หน้าเว็บอาจตรวจข้อมูลให้ผู้ใช้เห็นทันทีได้ แต่ไม่ควรเชื่อใจเพียงชั้นเดียว เพราะคำขอสามารถถูกส่งตรงมาที่ API โดยไม่ผ่านหน้าเว็บได้ API จึงต้องตรวจซ้ำเสมอ เพื่อให้ข้อมูลที่เข้าไปอยู่ในฐานข้อมูลสะอาดและเชื่อถือได้

### ทำไมเลือก SQLite

SQLite เป็นฐานข้อมูลแบบ Zero-Configuration คือไม่ต้องติดตั้งหรือตั้งค่าเซิร์ฟเวอร์ฐานข้อมูลแยกต่างหาก เพราะข้อมูลทั้งหมดอยู่ในไฟล์เดียว (`campus.db`)

- **ประหยัดทรัพยากร** ไม่ต้องมีโปรแกรมฐานข้อมูลรันค้างไว้อีกตัว
- **พกพาง่าย (Portable)** จะย้ายหรือสำรองข้อมูลก็แค่คัดลอกไฟล์เดียว
- **เริ่มใช้ได้เร็ว** ใครโคลนโปรเจกต์ไปก็รัน `npm run db:setup` แล้วใช้งานได้เลย
- **เหมาะกับขนาดงาน** ระบบบริการระดับวิทยาเขตต้องการความเรียบง่ายและปรับใช้ (Deploy) ได้ไว มากกว่าความซับซ้อนของฐานข้อมูลขนาดใหญ่

### ทำไมโหมด Production เปิด URL เดียว

ตอนพัฒนาเราแยกรัน Frontend กับ API คนละพอร์ตเพื่อความสะดวก แต่ตอนใช้งานจริง การให้ Express เสิร์ฟทั้งหน้าเว็บและ API บนพอร์ตเดียวมีข้อดีคือ

- ติดตั้งง่าย มีแค่ 1 โปรเซสที่ต้องดูแล
- ไม่ต้องตั้งค่า CORS ซับซ้อนระหว่างสองโดเมน
- ผู้ใช้เข้าผ่านที่อยู่เดียว จำง่ายและจัดการง่าย

### ทำไมตั้งค่าผ่าน Environment Variables

ค่าที่เปลี่ยนไปตามเครื่องหรือสภาพแวดล้อม เช่น พอร์ต ที่อยู่ไฟล์ฐานข้อมูล หรือ URL ของ Frontend ไม่ควรถูกเขียนฝังไว้ในโค้ด การแยกไว้ในไฟล์ `.env` ทำให้เปลี่ยนค่าได้โดยไม่ต้องแก้โค้ด และเครื่องของแต่ละคนก็ตั้งค่าต่างกันได้โดยไม่ชนกัน
