# Database Choices

เอกสารนี้อธิบายเหตุผลที่เลือกฐานข้อมูลของโปรเจกต์ และสิ่งที่ต้องแก้หากวันหนึ่งต้องเปลี่ยนไปใช้ฐานข้อมูลอื่น

---

## 1. ทำไมโปรเจกต์นี้เลือก SQLite แทน MongoDB

ข้อมูลในระบบมีโครงสร้างแน่นอนและมีความสัมพันธ์กันชัดเจน เช่น คำร้อง (`requests`) ต้องผูกกับผู้แจ้ง (`users`) การใช้ SQLite ซึ่งเป็นฐานข้อมูลแบบ Relational จึงตอบโจทย์เรื่องการเชื่อมตารางมากกว่า

นอกจากนี้ SQLite ยังเก็บข้อมูลเป็นไฟล์เดียวในเครื่อง ทำให้รันง่าย ไม่ต้องเปิดเซิร์ฟเวอร์ฐานข้อมูลแยกให้ซับซ้อน เหมาะกับแอปขนาดเล็กในวิทยาเขต

| ประเด็น | SQLite | MongoDB |
|---|---|---|
| รูปแบบข้อมูล | ตารางที่มีโครงสร้างแน่นอน | เอกสารแบบยืดหยุ่น |
| ความสัมพันธ์ระหว่างข้อมูล | เชื่อมตารางได้ตรงไปตรงมา | ต้องออกแบบเอง |
| การติดตั้ง | ไม่ต้อง ใช้ไฟล์เดียว | ต้องมีเซิร์ฟเวอร์ฐานข้อมูลแยก |
| ความเหมาะสมกับโปรเจกต์นี้ | เหมาะ | เกินความจำเป็น |

## 2. ถ้าวันหนึ่งต้องเปลี่ยนไป MongoDB จะกระทบชั้นไหนบ้าง

กระทบ 2 ชั้น คือ **service** และ **controller**

### Service

ต้องแก้โค้ดที่ดึงข้อมูลทั้งหมด เพราะจากเดิมที่อ่านไฟล์ในเครื่องได้ทันที ต้องเปลี่ยนไปดึงข้อมูลผ่านเครือข่ายของ MongoDB ฟังก์ชันใน service จึงต้องเปลี่ยนเป็นแบบ `async` ทั้งหมด

### Controller

กระทบตามไปด้วย เพราะเมื่อ service กลายเป็น `async` (คืนค่าเป็น Promise) ตัว controller ก็ต้องใส่ `async/await` เพื่อรอให้ service ดึงข้อมูลเสร็จก่อน จึงจะส่งคำตอบกลับไปหาผู้ใช้ได้

## 3. async จำเป็นเมื่อไร ไม่จำเป็นเมื่อไร

**จำเป็นเมื่อ** มีการทำงานที่ต้องรอข้อมูลข้ามเครือข่ายหรือจากเซิร์ฟเวอร์อื่น (Network I/O) เช่น การต่อ MongoDB หรือเรียก API เพื่อไม่ให้โปรแกรมค้างระหว่างรอ

**ไม่จำเป็นเมื่อ** การประมวลผลจบในเครื่องตัวเองแบบรวดเร็ว (Local / In-Memory) เช่น การอ่านไฟล์ SQLite ในเครื่องผ่าน `node:sqlite` ที่ได้ผลลัพธ์ทันที
